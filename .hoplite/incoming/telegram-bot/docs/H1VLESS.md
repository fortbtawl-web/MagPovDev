# Интеграция с H1//VLESS (H1Cloud)

## Что установлено

H1Cloud подтвердил, что отдельная панель Remnawave не предоставляется, а сервера можно бесплатно переустановить под систему **H1//VLESS** с собственной панелью.

Официальной публичной документации API на сайте h1cloud.net найти не удалось. Контракт API взят **из исходного кода самой ноды**, опубликованного разработчиком H1Cloud:

- репозиторий установщика ноды: <https://github.com/h1gurodev/h1cloud-vless> (`main.sh`, класс `Handler`, сервер `H1CloudVPNAPI/1.0`);
- пример бота разработчика: <https://github.com/h1gurodev/h1cloudvless-vpn-sell> (`vpnsell/h1cloud.py`).

Это **API управления VPN-клиентами на ноде**, а не API управления VPS в кабинете H1Cloud. Их нельзя путать.

## Используемые методы (проверены по исходнику)

Базовый URL: `https://<IP ноды>:<API-порт>/api`. Авторизация: заголовок `Authorization: Bearer <API-токен ноды>` (нода также принимает `X-API-Key`).

| Наш метод (`backend/integrations/vpn/base.py`) | Вызов ноды | Ответ |
|---|---|---|
| `health_check` | `GET /health` + `GET /clients` (проверка токена) | `{"ok":true,"service":"vpn-api"}` |
| `create_client` | `POST /create {name, days, device_limit}` → `PATCH /edit {name, expires_at}` | `201 {"ok":true,"client":{...}}`, `409 user_already_exists` |
| `get_client` | `GET /clients/{name}` | `{"ok":true,"client":{...}}`, `404 user_not_found` |
| `extend_client` | `PATCH /edit {name, expires_at:<unix>}` | `{"ok":true,"client":{...}}` |
| `suspend_client` / `resume_client` | `PATCH /clients/{name}/ban {reason}` / `.../unban` | `{"ok":true,...}` |
| `revoke_client` | `DELETE /clients/{name}` | `{"ok":true,"deleted":name}`; `404` считается успехом (клиента уже нет) |
| `get_subscription_link` | поле `subscription_url` (или `sub_url`, `link`) клиента | |

Поля клиента, которые читает адаптер: `uuid`, `name`, `status` (`active`/`banned`), `expires_at` (unix-время), `subscription_url`, `sub_url`, `link`, `device_limit`, `devices_count`, `online`. Имя клиента должно соответствовать `^[A-Za-z0-9._-]+$`. Мы генерируем имена вида `sv<telegram_id>x<hex>`.

## Как устроена выдача

- **Один ключ на устройство.** Каждое «устройство» в боте — отдельный клиент на выбранной ноде. Лимит тарифа = число ключей. На ноде у каждого ключа `device_limit` из настройки `node_client_device_limit` (по умолчанию 1), чтобы одним ключом нельзя было делиться.
- **Идемпотентность.** Повторное создание с тем же именем возвращает `409`. Адаптер в этом случае читает существующего клиента. Срок задаётся абсолютным `expires_at`, поэтому повтор безопасен.
- **Подтверждение.** Устройство становится `active` только после успешного ответа ноды. При таймауте или недоступности ноды оно остаётся `pending`/`revoking`, операция ставится в очередь `vpn_operations`, и воркер повторяет её с экспоненциальной паузой (до 20 попыток).
- **Сверка.** Раз в ~10 минут воркер сравнивает БД с нодой. Пропавшего клиента он пересоздаёт, расхождение срока исправляет, бан/разбан синхронизирует.
- **Lifetime.** Нода требует конкретную дату окончания, поэтому ключ Lifetime получает технический срок (`lifetime_node_horizon_days`, по умолчанию 365 дней). Воркер продлевает его автоматически. В БД у подписки `is_lifetime=true` и `expires_at=NULL`.

## Проверено на реальных нодах (28.10.2026)

Панели SpirittVPN — **h1vless 2.7.3** (собственная панель H1, не 3x-ui).

- API доступен на порту панели: `http://<хост>:<порт_панели>/api`. Токен — «API-токен» панели. При повторном входе он не меняется. Передаётся в `Authorization: Bearer …` (или `X-API-Key`).
- Боту за пределами РФ нужен адрес `direct-<хост>`. У Польши основной адрес `pl3.h1cloud.net` ведёт на неработающий relay, а `direct-pl3` отвечает.
- Ссылки `vless://` приходят в поле `inbound_links` (tcp/grpc/xhttp Reality), подписка — в `sub_url`. Адаптер берёт TCP-ссылку и показывает пользователю подписку.
- Проверка здоровья ноды теперь включает TCP-проверку публичных VPN-портов из `GET /inbounds`. Если панель отвечает, но VPN-порты недоступны (как у Польши: relay `*.pl3.h1clayd.click` не отвечает), нода помечается недоступной. Бот не создаёт на ней ключи и предлагает выбрать другую страну. Смена локации на недоступную ноду отклоняется **до** отзыва старого ключа.

| Нода | Панель | VPN-трафик | Статус в боте |
|---|---|---|---|
| 🇩🇪 Германия | ✅ | ✅ выход DE (Франкфурт) | выдаёт ключи |
| 🇫🇮 Финляндия | ✅ | ✅ выход FI (Хельсинки) | выдаёт ключи |
| 🇺🇸 США | ✅ | ✅ выход US | выдаёт ключи |
| 🇵🇱 Польша | ✅ (через direct-) | ❌ ссылки ведут на мёртвый relay H1Cloud; напрямую на IP сервера трафик идёт | «временно недоступна» |
| 🇷🇺 Россия | ❌ порт принимает соединение, но не отвечает (после restart тоже) | — | «временно недоступна» |

Польша и Россия включаются автоматически: как только H1Cloud починит relay/панель, ближайшая проверка воркера (≈ каждые 5 минут) снимет флаг недоступности.

## Что нужно от владельца

1. Решить, переустанавливать ли сервера под H1//VLESS. **Переустановка уничтожает данные на сервере. Бот её не выполняет.** Делается в кабинете H1Cloud или через поддержку только после вашего решения.
2. Для каждой из 5 нод собрать:
   - URL API: `https://IP:порт/api`. Порт указан в панели ноды; в коде ноды по умолчанию используется `API_PORT`.
   - API-токен: из панели H1//VLESS (вход в панель возвращает токен API) или из файла `api_token.txt` в каталоге данных ноды.
3. Заполнить `VPN_NODES` и `VPN_NODE_<КОД>_TOKEN` в `.env`.
4. Проверить: админ-панель → «VPN-инфраструктура» → «Проверить сейчас». Также можно в боте `/admin` → «🌍 VPN-ноды».
5. Если нода работает на самоподписанном сертификате, установить `VPN_VERIFY_TLS=false`. Лучше поставить на ноду нормальный сертификат.

## Управление пятью серверами из одной панели

Код ноды поддерживает федерацию (`/fed/*`, `/nodes/join`, `/peers`): ноды можно связать между собой. Мы её **не используем**: каждая нода подключается напрямую своим URL и токеном. Так проще, надёжнее и не зависит от работы одной главной ноды.

## Что проверено вживую

- Адаптер (без моков) на панелях DE/FI/US/PL: создание, повторное создание без дубля, продление с точным сроком, бан/разбан, статус, удаление и повторное удаление.
- Сервисы бота + локальная PostgreSQL + реальные панели: админ-выдача, 3 устройства (DE/FI/US) с реальными ссылками своих локаций, лимит устройств, продление (срок на нодах = срок в БД), приостановка/возобновление, смена локации, отказ для PL/RU, сверка без расхождений.
- Тестовые клиенты удалены; существующий клиент `svtestde92f8f3` не тронут.

## Одна подписка на все локации и автовыбор по пингу

- В боте появляется локация **«🌐 Все локации (автовыбор)»** (код `all`, страна `ZZ`). Она создаёт одного клиента с одним UUID на хабе (Германия) и на остальных нодах с токеном через `/fed/lproxy/<id сервера H1Cloud>/create` + `/fed/origin`. Продление, бан и удаление, выполненные на хабе, сами доходят до остальных нод. Нужен только токен хаба. Реализация: `backend/integrations/vpn/h1federated.py`.
- Недостающие на нодах клиенты создаются заново при чтении (`get_client`, не чаще раза в 10 минут); недоступная нода не мешает выдаче ключа.
- Автовыбор — функция панели хаба: `POST /server/sub-auto {"enabled": true, "hosts": [], "name": "..."}`. Добавляет в подписку группу «Автовыбор» (Xray balancer `leastPing` + observatory). Поддерживают Happ, Hiddify/sing-box, Mihomo.
- Отключить: в панели хаба «Автовыбор» → выключить, или `POST /server/sub-auto {"enabled": false}`. Отключить локацию «Все локации» в боте: `VPN_ALL_ENABLED=false`.
- Один ключ — одно устройство (`node_client_device_limit=1`): панель отдаёт подписку только первому устройству.

## Что не проверено

- Работа бота в реальном Telegram и с базой Neon: у агента нет доступа к серверу бота (57249).
- Польша и Россия до исправления инфраструктуры на стороне H1Cloud.
